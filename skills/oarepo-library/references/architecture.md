# Generic oarepo library architecture

**Scope:** this applies to every oarepo-* repo - both plain extension packages (oarepo-doi, oarepo-glitchtip,
oarepo-runtime, ...) and to oarepo-model itself, since oarepo-model's own generated `Ext` class (see
[model_architecture.md](model_architecture.md)) is built on exactly this same pattern. If the repo you're in
also defines `Preset`/`Customization`/`DataType` subclasses or imports `oarepo_model`, read
`model_architecture.md` in addition to this file - it does not replace it.

## The Flask extension pattern

Every oarepo library that needs runtime state (config defaults, a service, a client) exposes it as a Flask
extension with the same three-method shape, confirmed identical (down to the attribute name convention) in
oarepo-model, oarepo-doi, and oarepo-glitchtip:

```python
class OARepoXExt:
    def __init__(self, app: Flask | None = None) -> None:
        if app:
            self.init_app(app)

    def init_app(self, app: Flask) -> None:
        self.app = app
        app.extensions["x-key"] = self      # look this key up via a proxies.py LocalProxy, not by re-import
        self.init_config(app)

    def init_config(self, app: Flask) -> None:
        # merge defaults without clobbering a value the host app already set
        app.config.setdefault("X_SOME_SETTING", DEFAULT_VALUE)
```

Wired up purely through entry points in `pyproject.toml` - there is no other registration mechanism:

```toml
[project.entry-points."invenio_base.apps"]
oarepo_x = "oarepo_x.ext:OARepoXExt"
[project.entry-points."invenio_base.api_apps"]
oarepo_x = "oarepo_x.ext:OARepoXExt"
# optional, for a callable that needs the *fully* initialized app (all extensions loaded, blueprints registered):
[project.entry-points."invenio_base.finalize_app"]
oarepo_x = "oarepo_x.ext:finalize_app"
[project.entry-points."invenio_base.api_finalize_app"]
oarepo_x = "oarepo_x.ext:finalize_app"
```

`invenio_base.apps` registers the extension against the (Jinja/UI) app; `invenio_base.api_apps` against the
API-only app - most extensions register the same class under both unless they genuinely only make sense on
one side. `finalize_app`/`api_finalize_app` run once every other extension's `init_app` has already run (e.g.
`oarepo-glitchtip`'s `finalize_app` calls `app.before_request(...)` - registering a hook that depends on
nothing else being initialized first).

### `config.py`: defaults, never overrides

Config modules export plain module-level constants (`RDM_PERSISTENT_IDENTIFIER_PROVIDERS = [...]`) that
`init_config` merges into `app.config` with `setdefault(...)`, or by checking "is my thing already in this
list" before appending (`oarepo-doi`'s `init_config` checks `any(provider.name == "datacite" for provider in ...)`
before extending the providers list). **Never blindly overwrite `app.config[KEY]`** - a host application (or
another extension loaded first) may have already customized it; the whole point of `setdefault`/append-if-
missing is that the host app's own `invenio.cfg` always wins.

### `proxies.py`: how other code reaches the extension

```python
from flask import current_app
from werkzeug.local import LocalProxy

current_x = LocalProxy(lambda: current_app.extensions["x-key"])
```

This is the only sanctioned way for other modules (services, resources, CLI commands) to reach the
extension instance - never `import` the `Ext` class and instantiate/reach into it directly, and never reach
into `current_app.extensions["x-key"]` inline at every call site; go through the one proxy so there's a
single place to change the lookup key.

## Package layout is a per-repo choice

oarepo-model uses `src/oarepo_model/`; oarepo-doi and oarepo-glitchtip use a flat `oarepo_doi/`/
`oarepo_glitchtip/` at the repo root. Both work with zero extra `[tool.hatch.build]` configuration in
`pyproject.toml` in the three repos checked - hatchling's default package auto-detection handles either
layout by matching (a normalized form of) `[project.name]`. **Do not assume `src/` layout** when writing a
path, an import, or a `find`/`grep` command against an unfamiliar oarepo-* repo; check `pyproject.toml` and
the actual top-level directories first.

## Other conventions to expect

- **CLI commands**: a `cli.py` module defining click commands, registered via an
  `[project.entry-points."oarepo.cli"]` (or, in oarepo-model, an `invenio.cfg`-visible `oarepo-cli` plugin)
  entry rather than any ad-hoc script.
- **Alembic migrations**: DB-backed extensions (oarepo-doi) ship an `alembic/` directory with version
  migrations for their own tables; a `ty.toml`/`lint` config generated by `oarepo-cli` explicitly excludes
  `**/alembic/**` from type checking (alembic revision files are largely boilerplate/generated).
  `./run.sh alembic ...` drives these, not raw `alembic` commands.
- **Translations**: a package with user-facing strings ships `babel.ini` plus a `translations/<lang>/` tree;
  `./run.sh translations` (wrapping `oarepo-tools make-translations`) extracts/compiles them - don't hand-edit
  compiled `.mo` files.
- **`invenio_administration.views` entry points**: packages exposing an admin UI panel register
  `AdministrationView` subclasses this way rather than wiring a blueprint by hand.

## Deciding what kind of library you're writing/reviewing

Ask: does this package need to add or reshape *record fields/schemas/mappings* for a model the host
application defines, or does it add cross-cutting *behavior/config* (a PID provider, an error-tracking
integration, a permission policy)? The former is what `oarepo_model`'s preset/customization/datatype system
exists for (see [model_architecture.md](model_architecture.md)); the latter is almost always better served by
the plain extension pattern above - most oarepo-* packages, including fairly substantial ones like
`oarepo-doi`, never need `oarepo_model` at all.
